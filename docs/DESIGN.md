# وثيقة التصميم

هذه وثيقة حيّة يتم تحديثها باستمرار. يجب تسجيل أي قرار عند تغييره، أما القرارات الكبيرة فيتم توثيقها بشكل منفصل داخل مجلد `adr/`.

## الأهداف

1. إعادة جميع وظائف البوت القديم، وتشمل:
   - الموسيقى.
   - قنوات الصوت المؤقتة للحفلات.
   - رسائل الترحيب.
   - الإشراف وإدارة السيرفر.
   - نظام Dżajco.

   مع بناء قاعدة برمجية سهلة التوسعة، بحيث يمكن إضافة كل ميزة بشكل مستقل دون تعقيد بقية المشروع.

2. يجب أن يعمل كل أمر بطريقتين:
   - أوامر Slash مثل `/play`.
   - أوامر Prefix مثل `!play`.

   ويجب تعريف الأمر مرة واحدة فقط، دون تكرار الكود.

3. كل ميزة عبارة عن وحدة مستقلة (Module):
   - إضافة ميزة جديدة لا تتطلب تعديل الميزات الأخرى.
   - إمكانية اختبار كل ميزة دون الحاجة إلى الاتصال بـ Discord.

## المكونات

```text
بوابة Discord
     │
     ▼
  apps/bot
     │
     ▼
  registry
     │
     ▼
  الوحدات (general, music, party, ...)
     │
     ├── Postgres: إعدادات السيرفر والتحذيرات وغيرها.
     ├── Redis: التخزين المؤقت للبادئة وفترات الانتظار.
     └── Lavalink: تشغيل الموسيقى من YouTube وBandcamp وغيرها.
```

## الحزم البرمجية

| الحزمة | الاعتماديات | الوظيفة |
|---|---|---|
| `core` | أنواع أحداث discord.js | نموذج الأوامر والوحدات، سجل الأوامر، تحليل أوامر Prefix، موزع الأوامر، نظام التسجيل، والأدوات المشتركة `helpers.ts`. لا تنفذ أي عمليات إدخال أو إخراج. |
| `db` | `Bun.SQL` | ملفات SQL، وترحيلات قاعدة البيانات، ومشغل الترحيلات، والمستودعات، وأنواع صفوف قاعدة البيانات. |
| `kv` | Bun `RedisClient` | واجهة `KeyValueStore`، ومحول Redis، ونسخة وهمية داخل الذاكرة للاختبارات، واختبارات مشتركة للتحقق من صحة التنفيذ. |
| `modules/*` | `core` والواجهات التي تعلن عنها الوحدة | كل وحدة مسؤولة عن ميزة واحدة. يمنع عليها استيراد `apps/bot` أو عملاء قاعدة البيانات أو الوحدات الأخرى. |
| `apps/bot` | جميع الحزم السابقة | نقطة تجميع المشروع، والمكان الوحيد الذي يتعامل مع كائنات discord.js أثناء التشغيل. |

# القرارات الأساسية

## 1. أمر واحد بطريقتين للتشغيل

يتم تعريف خيارات الأمر مرة واحدة باستخدام `defineCommand`.

- يتم إنشاء نسخة Slash تلقائيًا باستخدام `toSlashCommand`.
- يتم تحليل نسخة Prefix باستخدام `parsePrefixArgs`، مع قراءة الوسائط بالترتيب نفسه.

لا تتعامل الوحدات مباشرة مع Discord، وإنما تستقبل `CommandContext` الذي يحتوي على:

- `args`: الوسائط التي أدخلها المستخدم.
- `caller`: الشخص الذي نفذ الأمر.
- `reply`: وظيفة إرسال الرد.
- `defer`: وظيفة تأجيل الرد.

### القواعد

- يجب وضع الخيارات الإلزامية قبل الخيارات الاختيارية.
- الخيار النصي الأخير فقط يمكنه استخدام `rest: true`، لاستقبال بقية السطر بالكامل.
- هذا يمنع التعارض بين طريقتي تنفيذ الأمر.
- الخيار الذي يحمل `prefixOnly: true` لا يظهر في أمر Slash، ويُستخدم عندما يتم جمع المدخلات بطريقة أخرى، مثل النوافذ المنبثقة (Modal).
- في هذه الحالة يتفرع التنفيذ باستخدام `ctx.canShowModal`.

راجع ADR 5.

## 2. الأوامر الفرعية

يمكن للأمر الواحد أن يحتوي على عدة إجراءات فرعية، مثل:

```text
/prefix set
!prefix set ?
```

بدلًا من استخدام `options` و`run` معًا.

- يتم إنشاء كل أمر فرعي باستخدام `defineSubcommand`.
- لكل أمر فرعي خياراته الخاصة.
- يتم تحويل الأوامر الفرعية إلى خيارات `SUB_COMMAND` في أوامر Slash.
- في أوامر Prefix، تحدد الكلمة الأولى الإجراء الفرعي المطلوب.

إذا لم يكتب المستخدم اسم الإجراء الفرعي أو كتب اسمًا غير صحيح، تظهر رسالة خطأ باللغة البولندية تعرض أسماء الإجراءات الصحيحة.

يتم تمرير اسم الإجراء المختار عبر `ctx.subcommand`.

أما الصلاحيات:

- صلاحيات الأمر الأساسي تتحول إلى `default_member_permissions` في Discord.
- صلاحيات الأمر الفرعي يتم التحقق منها عند تنفيذه فقط.

## 3. ملكية الوحدات وإيقاف التشغيل

يحتفظ سجل الأوامر (Registry) بمعلومات عن الوحدة التي سجلت كل أمر باستخدام `moduleOf`.

كما تحتفظ الدالة `events()` بمعالجات الأحداث بالشكل التالي:

```ts
{ module, handler }
```

وهذا يسمح للبوت بتطبيق إعدادات تفعيل وتعطيل الوحدات لكل سيرفر من مكان مركزي، بدلًا من جعل كل وحدة تتحقق من إعداداتها بنفسها.

يمكن لأي وحدة تعريف الدالة:

```ts
dispose()
```

وعند إيقاف البوت، تستدعي `apps/bot` هذه الدالة لجميع الوحدات قبل إغلاق اتصال Discord.

## 4. الأزرار والقوائم والتنقل بين الصفحات

تُرسل الردود مع `components` على شكل بيانات عادية.

يتم تعريف معالجات الأزرار والقوائم باستخدام:

- `defineButton`
- `defineSelect`

داخل `BotModule.components`.

عند الضغط على زر، يتم توجيه الطلب باستخدام `custom_id` بالصيغة التالية:

```text
<module>:<component>:<owner>:<data>
```

يتم التحقق من أن الوحدة مفعّلة، وأن المستخدم يمتلك صلاحية استخدام المكوّن.

إذا ضغط شخص غير صاحب الأمر على زر خاص، يتم رفض الطلب برسالة خاصة (Ephemeral).

### تخزين حالة الأزرار

- البيانات الصغيرة يتم وضعها داخل `data`.
- البيانات الكبيرة يتم تخزينها في `KeyValueStore` لمدة 15 دقيقة.
- عند انتهاء صلاحية القائمة تظهر الرسالة:

`انتهت صلاحية هذه القائمة`

تتوفر `createComponentStateStore` داخل Core، لكنها غير مربوطة مباشرة بنقطة تجميع المشروع. أول وحدة تحتاج إليها تنشئها باستخدام `KeyValueStore` الذي تستقبله.

### نظام التنقل بين الصفحات

تقوم `createPaginator` بإنشاء أزرار التنقل بالشكل التالي:

```text
◀ | الصفحة N/M | ▶
```

يجب أن يبقى `custom_id` ضمن حد Discord البالغ 100 حرف، لذلك يجب إبقاء البيانات قصيرة أو استخدام مفتاح لحالة مخزنة.

أي ضغطة زر لا تتم الإجابة عليها من المعالج، يتم تأكيدها تلقائيًا.

تعمل الردود مع أوامر Slash وPrefix بالطريقة نفسها.

### قوائم اختيار المستخدمين

تضيف `defineUserSelect` قائمة اختيار مستخدم واحد:

```ts
{ type: "user-select" }
```

وتشغل صفًا كاملًا.

يحصل المعالج على معرّف المستخدم المختار داخل:

```ts
ctx.values
```

إذا كان المكوّن يحمل:

```ts
public: true
```

فيمكن لأي شخص استخدامه دون التحقق من ملكية الأمر.

في هذه الحالة يحمل `custom_id` القيمة:

```text
PUBLIC_OWNER (*)
```

ويجب أن ينفذ المعالج العملية اعتمادًا على `ctx.user`، أي الشخص الذي ضغط على الزر.

تبقى قيود السيرفر والصلاحيات وحالة الوحدة مطبقة.

كما يتحقق المحول من أن نوع التفاعل مطابق لنوع المكوّن: زر أو قائمة نصية أو قائمة مستخدمين.

## 5. النوافذ المنبثقة (Modals)

يتم تعريف النماذج باستخدام `defineModal`.

يمكن أن يحتوي النموذج على خمسة حقول كحد أقصى من الأنواع التالية:

- نص.
- قائمة اختيار.
- قناة.
- مستخدم.
- ملف.

تفتح الوحدة النموذج باستخدام:

```ts
ctx.showModal(modal.build(ctx.user.id, data))
```

وذلك من أمر Slash أو معالج زر أو قائمة.

عند إرسال النموذج، يستقبل المعالج القيم داخل:

```ts
ctx.values
```

### القيود

- أوامر Prefix لا تستطيع فتح النوافذ المنبثقة.
- في Prefix تكون قيمة `ctx.canShowModal` هي `false`.
- يجب توفير طريقة إدخال بديلة باستخدام الوسائط العادية.
- يتم التحقق من حدود النماذج عند تشغيل البوت.

يمكن لحقل المستخدم استقبال عدة أشخاص باستخدام `minValues` و`maxValues`، ويتم تمريرهم كمصفوفة `string[]`.

أما حقل الملفات فيقبل ملفًا واحدًا، ويتم التحقق من نوع الملف وحجمه عند الإرسال.

بيانات الملف `ModalFile` تحتوي على:

- `url`: رابط الملف.
- `name`: اسم الملف.
- `contentType`: نوع الملف.
- `size`: حجم الملف.

راجع ADR 6.

## 6. الأوامر الخاصة

تحدد `contexts` الأماكن التي يمكن استخدام الأمر فيها:

- `guild`: داخل السيرفر.
- `bot-dm`: في الرسائل الخاصة مع البوت.
- `private-channel`: في القنوات الخاصة أو المجموعات.

كما تحدد نوع تثبيت التطبيق:

- `guild`: تثبيت على السيرفر.
- `user`: تثبيت على حساب المستخدم.

الافتراضي هو السيرفر فقط.

الأمران `/help` و`/ping` يعملان في جميع الأماكن المسموح بها، أما بقية الوحدات فتبقى مخصصة للسيرفرات.

### نشر الأوامر تلقائيًا

يقوم البوت بنشر أوامره بنفسه عند التشغيل:

1. إذا تم تحديد سيرفر تطوير، يتم النشر داخله.
2. إذا لم يتم تحديد سيرفر تطوير، يتم النشر عالميًا.

ولا يعيد النشر إلا عندما يختلف تعريف الأوامر لدى Discord عن التعريف الحالي.

المتغير:

`COMMANDS_AUTO_DEPLOY`

يمكنه إيقاف النشر التلقائي.

كما يمكن تنفيذ النشر يدويًا باستخدام:

`commands:deploy`

عند استخدام `DEPLOY_GLOBAL` يتم النشر عالميًا مع إفراغ أوامر سيرفر التطوير، تمامًا مثل سكربت النشر.

في وضع سيرفر التطوير، لا يتم تعديل الأوامر العالمية، ويظهر تحذير إذا كانت هناك أوامر عالمية؛ لأن أعضاء سيرفر التطوير قد يرون الأوامر مرتين.

يتم إرسال `integration_types` و`contexts` للأوامر العالمية، ولا يتم إرسالهما لسيرفر التطوير.

أما أوامر Prefix داخل الرسائل الخاصة فتستخدم البادئة الافتراضية.

الأمر المخصص للسيرفر فقط يعرض الرسالة:

`يعمل هذا الأمر في الخوادم فقط`

عند تثبيت البوت على حساب المستخدم فقط، لا يستطيع البوت إرسال رسائل مباشرة إلى القناة، لذلك تتم الردود عبر التفاعل نفسه.

كما تحمل `contexts` المكان الدقيق للتفاعل، حتى لا يتم الخلط بين محادثة البوت الخاصة ومحادثات المجموعات.

راجع ADR 7.

## 7. نظام المساعدة

الأمر:

```text
/help
!help
```

يفتح قائمة مساعدة خاصة (Ephemeral).

تحتوي القائمة على:

- صفحة رئيسية تعرض التصنيفات (الوحدات).
- عدد الأوامر في كل تصنيف.
- قائمة اختيار لفتح التصنيف.
- أزرار إضافة البوت إلى السيرفر أو إلى حساب المستخدم.

تعرض صفحة التصنيف ستة أوامر في كل صفحة باستخدام `createPaginator`.

كل أمر فرعي يظهر كمدخل مستقل، مع عرض صيغة Slash وصيغة Prefix.

تبقى قائمة التصنيفات متاحة للتنقل بينها، ويوجد زر باسم:

`الصفحة الرئيسية`

للعودة.

### إخفاء الأوامر غير المتاحة

عند كل عرض للقائمة، تتم إعادة مراجعة صلاحيات المستخدم:

- الأوامر التي لا يمتلك المستخدم صلاحياتها لا تظهر.
- الأوامر الموجودة داخل وحدات معطلة لا تظهر.
- الأوامر غير المتوافقة مع المكان الحالي لا تظهر.

المديرون يستطيعون رؤية جميع الأوامر.

يتم تحديد مكان الاستخدام بدقة:

- المحادثة الخاصة مع البوت تعرض الأوامر التي تسمح باستخدام `bot-dm`.
- المحادثة الجماعية تعرض الأوامر التي تسمح باستخدام `private-channel`.

في السيرفر الذي لا يكون البوت عضوًا فيه (تثبيت المستخدم)، وفي المحادثات الجماعية، تعرض القائمة صيغة Slash فقط، ولا تقرأ البادئة أو إعدادات تفعيل الوحدات.

كما يتجاوز نظام البوابة فحص تفعيل الوحدات في هذه السيرفرات.

تعرض الصفحة الرئيسية تلميحًا يوضح صيغة الأمر التي استخدمها العضو، مثل:

```text
!help komenda
/help komenda
```

يسمح سجل الوحدات بوجود 25 وحدة كحد أقصى، وهو الحد الأقصى لعناصر قائمة الاختيار.

أما الأمر:

```text
/help <command>
```

فيعرض أمرًا واحدًا مع تطبيق فلاتر الصلاحيات والمكان نفسها.

إذا كان اسم الأمر غير موجود أو مخفيًا بسبب الصلاحيات، تظهر رسالة عدم العثور نفسها.
